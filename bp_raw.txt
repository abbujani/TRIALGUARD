Below is the **complete implementation blueprint I would use for TrialGuard**, from an empty folder to a working hackathon submission.

The design stays tightly aligned with the supplied hackathon brief: the project must use Hindsight, make persistent memory central to the solution, solve a real professional workflow, demonstrate the value within a short demo, and clearly explain how Hindsight is used.   The submission also requires a GitHub repository, demo video, live demo, the specified content deliverables, and an explanation of Hindsight's use. 

# 1. First freeze the exact project scope

Do **not** build a complete clinical-trial management platform.

Your project should do one thing:

> **Help clinical-trial coordinators understand a participant's current problem by retrieving relevant historical interactions, interventions, and outcomes from long-term memory.**

### Primary persona

**Clinical Trial Coordinator**

### Primary entity

**Participant**

### Primary workflow

```text
New participant check-in
        â†“
Understand current issue
        â†“
Retrieve relevant participant history from Hindsight
        â†“
Connect current issue with historical events
        â†“
Surface previous outcomes
        â†“
Generate Coordinator Action Brief
        â†“
Retain the new interaction/outcome for future use
```

This is important because the official guide explicitly recommends **one workflow, one persona, and one clear value proposition**, rather than a huge prototype with many loosely connected features.

# 2. What TrialGuard actually solves

The central problem is **loss of longitudinal context**.

A participant might interact with the clinical-trial team many times:

```text
Month 1
   â†“
Month 2
   â†“
Month 3
   â†“
Month 4
   â†“
Month 5
   â†“
Month 6
```

A current complaint may only make sense when viewed against that history.

For example:

```text
Month 1
Dosage increase
      â†“
Nausea reported
      â†“
Documented intervention
      â†“
Symptoms improved

Month 3
Another dosage increase

Month 6
Nausea returns
Participant expresses frustration
Participant considers leaving
```

The critical information is spread across months.

A stateless LLM sees only:

```text
"Participant reports severe nausea and wants to leave."
```

TrialGuard sees:

```text
Current event
      +
Month 1 memory
      +
Month 2 outcome
      +
Month 3 dosage event
      â†“
Historical context
```

That is your entire product story.

# 3. Define what the agent is allowed to do

This should be fixed **before writing code**.

TrialGuard **can**:

* identify the current issue from a check-in;
* retrieve relevant historical memories;
* connect events across time;
* surface previous documented interventions and outcomes;
* identify that a similar event occurred previously;
* create a coordinator-facing summary;
* flag information for review or escalation according to the trial/site process.

TrialGuard **must not**:

* diagnose the participant;
* prescribe treatment;
* independently change a medication dosage;
* claim that an event caused another event merely because they occurred sequentially;
* decide whether a participant should remain in the trial;
* tell a participant to ignore symptoms;
* invent missing historical events.

So instead of:

> "Change the participant's dosage."

the system says:

> **"A similar event followed a previous dosage increase. A previously documented intervention was associated with improvement. Review this historical context with the appropriate clinical team."**

This keeps the project as **decision support**, not autonomous medical decision-making.

Also put this visibly in the prototype:

> **Prototype for hackathon demonstration using synthetic data. Not for clinical use or medical decision-making.**

I recommend this stack:

| Layer                | Technology                                |

| Frontend             | HTML + CSS + JavaScript                   |

This is deliberately simple.

You do **not** need React, Node.js, Spring Boot, MySQL, Docker, or a large agent framework to demonstrate the concept.

The important external components are Hindsight and the LLM.

The hackathon explicitly says Hindsight is mandatory and allows either Hindsight Cloud or the open-source version. 

For this project, I would use **Hindsight Cloud** because it removes a large amount of infrastructure work.

# 5. Why Hindsight Cloud is the better implementation route

The current Hindsight Cloud documentation provides a Python client:

```text
pip install hindsight-client
```

and connects using:

```python
from hindsight_client import Hindsight

client = Hindsight(
    base_url="https://api.hindsight.vectorize.io",
    api_key="your-api-key"
)
```

The Cloud setup also supports creating a memory bank and then using `retain`, `recall`, and related operations. ([Hindsight Cloud][1])

The official documentation currently exposes the Hindsight Cloud API as version 0.10.1. ([Hindsight API][2])

### Hindsight provides three operations that matter here

**Retain**

Store information in memory.

**Recall**

Retrieve relevant memories.

**Reflect**

Reason over remembered information and synthesize an answer. ([GitHub][3])

For TrialGuard, your main loop should be:

```text
RETAIN â†’ RECALL â†’ LLM ANALYSIS â†’ RETAIN OUTCOME
```

You can optionally use `reflect` for deeper memory analysis later.

# 9. Design your memory structure properly

This is one of the most important technical decisions.

Don't blindly send random JSON or raw database rows into Hindsight.

Hindsight's `retain` operation processes the supplied content, extracts structured memories, identifies entities and relationships, and indexes the information. ([Hindsight Cloud][4])

So give it **clear, meaningful event narratives**.

For example:

```text
Participant P402.
Trial: TRIAL-001.
Date: 2026-03-10.

Participant reported nausea following a recent dosage increase.
The participant described symptoms as moderate.
A meal-timing intervention was documented.
At the subsequent follow-up, symptoms were reported as improved.
```

This gives Hindsight useful information about:

```text
participant
date
symptom
event
intervention
outcome
relationship
```

---

# 10. Use timestamps aggressively

This project is fundamentally temporal.

Hindsight's current documentation says timestamps enable temporal retrieval and that temporal context should be provided when available. ([GitHub][5])

Every event therefore gets:

```text
occurred_at
```

For example:

```text
2026-03-10T10:00:00Z
```

Then when asking Hindsight about the Month 6 event, provide an appropriate `query_timestamp`.

This allows the system to reason about:

```text
before
after
recently
months earlier
previous episode
subsequent outcome
```

---

# 11. Use tags to isolate participants

This is another important engineering decision.

Suppose the bank contains:

```text
P101
P204
P402
P503
```

You do not want a query about P402 to accidentally retrieve P204's memories.

Use tags such as:

```text
participant:P402
trial:TRIAL-001
```

For a memory:

```python
tags=[
    "participant:P402",
    "trial:TRIAL-001"
]
```

When recalling:

```python
tags=[
    "participant:P402",
    "trial:TRIAL-001"
]
```

and use strict matching.

Hindsight currently supports tag filtering with modes including `all_strict`, which excludes untagged memories and requires all specified tags to match. ([GitHub][5])

For your prototype this means:

```text
Participant P402
      â†“
participant:P402
      +
trial:TRIAL-001
      â†“
Only P402 / TRIAL-001 memories
```

This also gives you something technically impressive to explain to judges.

# 13. Give every event a stable document ID

For example:

```text

checkin:P402:002
```

Hindsight's documentation recommends stable document identifiers rather than generating a new random ID on every write, which can create duplicates. Reusing a document ID can also be used to replace an earlier document where appropriate. ([GitHub][5])

For your project:

```python
document_id=f"checkin:{participant_id}:{checkin_id}"
```

# 14. What goes into SQLite versus Hindsight?

Use **both**, but for different purposes.

### SQLite

Store the application's exact records:

```text
participants
checkins
outcomes
agent_runs
```

### Hindsight

Store the information the agent needs to remember and retrieve:

```text
participant events
historical symptoms
interventions
outcomes
important interaction context
```

This distinction is useful because the Hindsight documentation explains that the retained content is transformed into extracted memories rather than simply being treated as a verbatim document store. ([Hindsight Cloud][4])

So:

```text
SQLite = application record
Hindsight = agent memory
```

That is a very clean architecture.

# 18. Implement the retain operation

Conceptually:

```python
def retain_checkin(
    participant_id,
    trial_id,
    checkin_id,
    occurred_at,
    text
):
    content = f"""
    Participant: {participant_id}
    Trial: {trial_id}
    Date: {occurred_at}

    Participant check-in:
    {text}
    """

    client.retain(
        bank_id=BANK_ID,
        content=content,
        context="clinical_trial_checkin",
        timestamp=occurred_at,
        document_id=f"checkin:{participant_id}:{checkin_id}",
        metadata={
            "participant_id": participant_id,
            "trial_id": trial_id,
            "event_type": "checkin"
        },
        tags=[
            f"participant:{participant_id}",
            f"trial:{trial_id}"
        ]
    )
```

This gives Hindsight a meaningful, timestamped event.

# 20. Build the Hindsight recall function

Your recall function should ask a **specific longitudinal question**.

Not:

```text
"Tell me about P402."
```

Instead:

```text
"Find relevant historical interactions for Participant P402
related to nausea, dosage changes, interventions, symptom outcomes,
withdrawal concerns, and similar recurring issues."
```

Then call Hindsight:

```python
result = client.recall(
    bank_id=BANK_ID,
    query=query,
    budget="mid",
    max_tokens=3000,
    query_timestamp=occurred_at,
    tags=[
        f"participant:{participant_id}",
        f"trial:{trial_id}"
    ],
    tags_match="all_strict",
    include_chunks=True,
    include_source_facts=True
)
```

Current Hindsight Recall uses semantic, keyword, graph, and temporal retrieval together, then fuses and reranks results. ([Hindsight Cloud][7])

That is excellent material for your technical explanation.

You can literally tell judges:

> **"Our retrieval isn't just vector similarity. Hindsight combines semantic, keyword, graph, and temporal retrieval to find the historical context relevant to the current event."**

That is a much stronger explanation than saying "we used a vector database."

---

# 21. Why `include_chunks=True` is useful

Hindsight generally returns structured memories.

For a hackathon demo, you also want to show where the memory came from.

The current documentation recommends `include_chunks=True` when the agent needs the original source text, and `include_source_facts=True` when you want provenance for observation-based memories. ([GitHub][8])

That allows your UI to show:

```text
Hindsight Memory

Month 1
"Participant reported nausea after dosage increase..."

Source:
checkin:P402:001
```

Now the judge can see the memory is **traceable**, not magically invented.

Groq's current documentation supports local function/tool calling, where the model requests a tool, your application executes it, and the result is sent back to the model for the final answer. ([GroqCloud][9])

# 26. Final output structure

Don't ask the final LLM for an unrestricted paragraph.

Have it generate a structured object.

Something like:

```json
{
  "current_issue": "...",
  "participant_concern": "...",
  "historical_matches": [
    {
      "date": "...",
      "event": "...",
      "relevance": "..."
    }
  ],
  "historical_pattern": "...",
  "previous_outcome": "...",
  "recommended_coordinator_action": "...",
  "safety_note": "..."
}
```

This makes your UI predictable.

Groq currently supports Structured Outputs with JSON Schema, including strict schema enforcement on supported models. Its documentation also notes that Structured Outputs and tool use are not currently supported together in the same request. ([GroqCloud][10])

That suggests a clean architecture:

```text
LLM call #1
Tool-calling agent
       â†“
Hindsight recall
       â†“
LLM call #2
Structured JSON final answer
```

This separation is preferable to trying to force tool calling and structured output into one request.



Hindsight's current learning architecture also supports automatically consolidated **observations** and manually curated **mental models** in addition to raw facts.
